## 0:30 – 2:00　整体结构（90 秒）

打开项目目录，只说层，不说细节：

```
backend/    FastAPI，三层：路由 → 业务服务 → partner 客户端
data/       两个 JSON，订单 + 698 条 SKU 全表，没有数据库
frontend/   Vue 3，4 个组件
```

两个关键词，各一句话：

- **纯函数分离**：`pricing.py` 只做金额计算，它不认识"订单号"也不认识"SKU"，
  输入是 `(rrp, qty, 税率)`，输出是金额。所以它能被单测穷举，也不受数据变更影响。
- **数据驱动**：业务代码里搜不到 `PO-20251130-00072`、搜不到 `TBAMET10`、搜不到 `1.10` 这个税率。
  换一份 `orders.json` 就是另一批订单，代码一行不动。

> 如果对方要看证据：在 IDE 里全局搜订单号 `PO-20251130-00072`，只在 `data/` 和 `tests/` 里命中，
> `backend/app/` 和 `frontend/src/` **零命中**。搜 `TBAMET10` 同理。

## 2:00 – 4:00　金额口径（最容易丢分的两分钟）

这一段**必须**在页面上指着讲，不要口述。

1. 指着订单 1 的汇总四行：
   ```
   小计（不含 GST）  A$1937.24
   GST（10%）        A$193.72
   运费              A$11.44
   总计              A$2142.40
   ```
   说：`1937.24 × 10% = 193.72`，`1937.24 + 193.72 + 11.44 = 2142.40`。**三处都能用计算器验。**

2. 讲舍入顺序，这是真正的技术点：
   > "题目给的是 `RRP / 1.10`，但没说舍到哪一步。这两种顺序实测会差钱：
   >
   > | 订单 | 单价先舍入 | 行合计后舍入 | 差 |
   > |---|---|---|---|
   > | 订单 1 | 1937.24 | 1937.28 | **0.04** |
   > | 订单 2 | 1504.54 | 1504.55 | **0.01** |
   >
   > 我选的是**单价先舍入到分**，因为发票上印的是单价，顾客自己乘一遍必须能对上。
   > 如果先乘再舍，顾客拿单价乘数量会差一分钱，这是对账投诉的经典来源。"

3. 讲一个防御性设计：
   > "Python 的 `round()` 是银行家舍入，`round(2.5) == 2`，做钱会出错。
   > 所以全程用 `Decimal` + `ROUND_HALF_UP`。而且我写了一条测试，
   > **用 AST 扫描整个 `backend/app` 目录，谁写 `round(` 测试就红**。
   > 三个月后别人接手，也不会悄悄改坏。"

4. 运费 GST 的处理，一句话带过（别在这纠缠）：
   > "运费我也是从接口拿的真实报价，含税全额单独一行，GST 行严格只算商品。
   > 另一种写法是把运费税并进 GST 行，总额一样，但 GST 就不等于 `Subtotal × 10%` 了，
   > 按题目公式就验算不上了，所以我放弃了那种写法。"

## 4:00 – 6:00　运费是真调接口（两分钟，最有说服力）

1. 打开 `http://localhost:8000/api/orders`（或在浏览器看 Network 里那条响应），指着 JSON 说：

   ```json
   "quote": {
     "strategy": "single_carton",   "request_count": 1,
     "carton": { "length": "30", "width": "20", "height": "12", "weight": "0.988" },
     "origin_used": { "suburb": "GLADESVILLE", "state": "NSW", "postcode": "2111" },
     "http_status": 200
   }
   ```

   > 别在页面上找这些——题目没要求展示，页面上只有业务字段。
   > 讲解时直接开 API 响应，反而证明"这些数字不是我编在前端的"。

2. 说清运费是怎么来的：
   > "运费不是本地公式算的，是 `POST /shipping/v1/prices/shipments` 的真实返回。
   > 但接口要的是'一个包裹的长宽高重量'，所以**装箱这件事必须由我决定**——
   > 这是一个明确的假设，不是它的返回值。"

3. **主动交代踩过的坑**（说明你会回头看自己的输出）：
   > "我第一版装箱是'高度 = 每个 SKU 高度 × 数量累加'，5 个 SKU 算出 `9×9×165 cm` 的药箱。
   > testbed 不校验尺寸上限，照样返回 200，我没报错。但这个尺寸物理上不成立，
   > 那个高度明显是在凑数。后来改成**体积法**：底面固定 30×20cm，
   > 高度 = 总体积 ÷ 底面积，再跟最高单件取大。算出来 12cm，可信。
   >
   > 这件事的教训是：**接口不报错 ≠ 你的假设是对的**。"

4. 讲起运地那个 400：
   > "`2111` 这个邮编在 testbed 里配 `RYDE` 会 400，配 `GLADESVILLE` 才 200。
   > 我没写死一个,而是做成候选链：环境变量 → 数据文件 → 逐个调 `/address` 校验，
   > 取第一个通过的。最终用了哪个，在 `quote.origin_used` 里能看到。"

## 6:00 – 7:30　降级（90 秒，现场演示）

**现场把 `.env` 改个名，清缓存，刷新浏览器。** 全程不重启服务。

```bash
mv .env .env.hidden
curl -X POST http://localhost:8000/api/cache/clear   # 必须清，否则命中 15 分钟缓存
```

> **注意顺序**：界面上没有清缓存按钮（那是运维操作，不该出现在订单页），
> 所以这一步要在终端里敲。只改名 + 刷新浏览器是不够的，会拿到旧结果。

> "现在页面变成了这样——注意它**没有**崩溃，也**没有**假装运费是 0 就算了。
> 运费那行是 `A$0.00`，下面跟着一行具体原因'未配置 AusPost 凭证'，
> 总计从 2142.40 变成 2130.96。
> 商品小计和 GST 一分钱没变——因为那部分只依赖 RRP 和数量，跟接口有没有通没关系。"

指着提示条说：

> "它说的是具体原因：'收货地信息不完整，无法向 AusPost 报价'，不是笼统的 'API 不可用'。
> 这个区分很重要：**地址缺失是数据问题，你去补地址；接口超时是系统问题，你去重试。**
> 使用者下一步该做什么完全不同，所以不能一句话糊过去。"

然后打开边界用例测试页（`http://localhost:5173/tests.html`）：

> "我在 `testcases_edge.json` 里造了三个故意坏掉的订单——SKU 不存在、数量写成 `'two'`、
> 收货地只有街道没有邮编。这三个不是崩溃，是**可预期的降级**：
> 坏的那一行标红、写明原因、不计入金额，其余行照算。
>
> 顺带说一句为什么它们不放在订单首页：**订单列表里不该出现虚构的坏数据**——
> 题目允许自造「合理的测试订单」，所以首页那 5 笔里另外 3 笔（`orders_generated.json`）
> 是合法数据，跟题目给的 2 笔真实订单一起正常算；只有故意造坏的这 3 笔才走测试链路。
> 使用者会分不清哪些是真订单。所以生产链路只加载 `orders.json`，
> 边界数据走单独的 `/api/testcases`，默认还是关的——要打开 `EXPOSE_TESTCASES=true` 才有。
> 回归主要靠 `pytest`，那 23 条断言离线就能跑完，不依赖页面。"

改回 `.env`，同样清缓存再刷新，页面恢复。

```bash
mv .env.hidden .env
curl -X POST http://localhost:8000/api/cache/clear
```

> **这里有个我自己踩的坑，值得说一句**：配置原本在进程启动时就被 `lru_cache` 锁死了，
> 改 `.env` 不重启根本不生效——也就是说"降级"这条最该被验证的路径，其实**演示不出来**。
> 后来改成用 `.env` 的 mtime 做指纹，文件一变就自动重读，
> 现在改名 → 清缓存 → 降级 → 改回 → 清缓存 → 恢复，全程 10 秒、不用重启。
> 这个问题是写讲解稿时才发现的，比写代码时发现更晚。

## 可能被追问的问题（准备好答案，别现编）

### Q1：为什么不用数据库？SQLite 不是更"正规"？

> "因为数据量是 698 条 SKU + 5 个订单，而且输入是外部文件。
> 上数据库唯一的收益是查询能力，但这里没有任何按条件查的需求；
> 成本是多一层部署依赖、多一个初始化步骤、演示时多一个失败点。
> 用 JSON 的话，对方打开 `data/orders.json` 就能看懂输入结构，讲解成本最低。
> 如果数据涨到几万条或者要支持写入，我会换 SQLite，接口层不用改。"

### Q2：运费凭什么这么算？你没有真实装箱算法。

> "对，我没有。真实装箱是 NP 难问题，而且需要纸箱规格库、堆叠规则、易碎品分区——
> 题目没给这些。所以我把它做成**显式假设**：一个标准箱、体积法推高度。
> 关键是三点：一、金额本身是接口返回的，不是我编的；二、假设写在 README 里，
> 还在页面上把实际箱型显示出来；三、如果以后有真实装箱规则，
> 只要替换 `build_single_carton()` 一个函数，接口层和前端都不用改。"

### Q3：你这么设计，如果 SKU 有 10 万条呢？

> "现在的 `data_loader` 是一次性加载全表进内存，698 条没问题，10 万条也还扛得住（几十 MB）。
> 瓶颈会先在 partner 接口的调用次数上，不在内存。
> 真要上量，第一件事是把 SKU 查询改成按需查（SQLite 索引），
> 第二件事是给报价加持久化缓存（现在只有内存 TTL）。
> 这两件事都不需要动业务逻辑，因为它们被 `data_loader` 和 `cache` 两层包着。"

### Q4：降级时金额还算吗？这不算给用户错误信息吗？

> "算，但**必须让人看见这是不完整的**。
> 如果不算，用户连商品本身值多少钱都看不到，页面一片空白，那才是真的没用。
> 所以我的做法是：商品金额（只依赖 RRP 和数量）永远算出来，
> 运费明确标成 `A$0.00` 并给出原因，总计下面那行小字说明运费未计入。
> 用户知道'这个数少了运费'，就能自己判断。"

### Q5：为什么前端不做金额计算？后端算完传过去不是多此一举？

> "两个原因。一、**单一数据源**：如果前端也有一份计算逻辑，两边口径一旦不一致，
> 你永远不知道哪个是对的。二、**可测试性**：后端能用 pytest 穷举边界，
> 前端算金额只能靠肉眼。所以前端只做 `toFixed(2)` 的显示格式化，
> 所有 `number` 运算都在后端。`frontend/src` 里找不到任何金额的加减乘除。"

### Q6：订单 2 上面写"运输中"，下面两票货都是"已送达"，这不矛盾吗？

> "矛盾，而且是**原始数据**里的矛盾，不是我算错的。
> `data/orders.json` 里订单 2 的 `status` 字段就写着 `In Transit`，
> 而 AusPost 两个单号都返回 Delivered。
>
> 我没有用轨迹去覆盖订单状态，三个原因：
> 一、订单状态是业务系统的状态，可能含退货、结算这些业务语义，跟承运商状态不是一回事；
> 二、数据驱动的前提是忠实呈现输入，代码里替用户'修正'数据，等于把上游的数据问题藏起来；
> 三、这种不一致恰恰是该被人看到的——它可能意味着订单系统没同步物流进度，是个真 bug。
>
> 我没有偷偷把它对齐成好看的样子。这件事我写在 README 的 2.6 节了。"

### Q7：如果让你重做一遍，哪里会不一样？

> "三处。
> 一、装箱假设我会一开始就写成配置（纸箱规格表），而不是先硬编码再改。
> 二、降级的原因码我会从第一天就做成枚举 + 中文映射，而不是先透出机器码再补翻译——
> 中间那版界面上出现过 `DESTINATION_INCOMPLETE` 这种裸常量，很难看。
> 三、我会更早去试**假数据**。testbed 对任意单号都返回样例数据这件事，
> 如果我一开始就试了 `INVALID123`，就不会差点把假单号放进演示里。"

## 一句话记住每个技术决策的理由

| 决策 | 一句话理由 |
|---|---|
| 整数分 + Decimal | `round()` 是银行家舍入，做钱会错 |
| 单价先舍入 | 顾客按单价乘数量必须对得上发票 |
| GST 只算商品 | 题目写的是 `Subtotal × 10%`，不能掺运费 |
| 运费走真接口 | testbed 是通的，mock 会白丢分 |
| 装箱用体积法 | 接口不报错不代表假设合理 |
| 起运地做候选链 | testbed 的 suburb/postcode 校验很死 |
| 降级说具体原因 | 地址缺失和接口超时的下一步动作不同 |
| 前端不算金额 | 两边各算一份，出错时不知道信谁 |
| 降级分支用构造响应测 | testbed 对任何单号都返回样例数据，假单号验不出来 |
